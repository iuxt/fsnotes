# Markdown 预览内存修复与性能实测

后续记录：[2026-10-08 渲染性能优化](RenderingOptimization.md)，包含共享解析、局部布局与异步预览管线；本文保留 2026-10-06 的修复实测。

测试日期：2026-10-06（Asia/Shanghai）。环境：Apple M1 Pro，10 核，16 GB，macOS 27.0.1，arm64 Release。
Git 基线：`c29cc389`；测试包含当前工作区的未提交更改。
测试应用使用独立 bundle identifier `es.fsnotes.previewbenchmark`、沙盒和临时笔记库。
正式源代码已修复；安装在 `/Applications` 的应用没有替换，用户笔记库没有写入。

## 修复结果

已修复 Markdown 的 C 解析资源泄漏、编辑器／控制器／预览之间的引用循环，以及字数统计和搜索任务对自身 BlockOperation 的循环引用。
关闭独立窗口时会完成待处理标签扫描、停止定时器、停止 WebView 加载并显式移除预览；窗口登记按控制器身份移除，关闭同一笔记的一个窗口不会移除另一个窗口。

最终回归完整完成，退出码 0，渲染无超时，生命周期与定时器检查均通过。
累计关闭 7 个独立窗口后，控制器、编辑器、文本处理器与 WebView 的弱引用均归零。
本次返回原生编辑器并等待 10 秒后的 RSS 总和为 237.2 MiB；修复前为 683.1 MiB，并有 5 个控制器与 5 个 WebView 长期保留。

## 原生解析器专项测试

直接编译正式 `FSNotesCore/Business/Markdown.swift`，不加载 WebKit。每种内容重复渲染 100 次；内存使用 `TASK_VM_INFO.phys_footprint`。

| 场景 | 修复前 physical footprint | 修复后 physical footprint |
|---|---:|---:|
| 100 次 4.1 KiB 小笔记 | 6.6 MiB | 3.3 MiB |
| 再渲染 100 次 515.6 KiB 长文 | 410.2 MiB | 10.0 MiB |

原实现长文测试平均每次留下约 4 MiB。正式实现现在使用 `defer` 释放节点树和 HTML 缓冲区，输出缓冲区通过 libcmark 的默认分配器释放；这些资源的所有权要求来自项目所用 libcmark 的头文件。
两种固定内容的 HTML SHA-256 与修复前一致。回归还要求预热后第 10 次到第 100 次的 physical footprint 增长不超过 8 MiB，用于捕获重新遗漏资源释放。
长文解析延迟中位数：6.70 ms → 6.29 ms。

## 完整应用测量

内存是各阶段末尾约 1 秒的应用及已确认 WebKit 进程 RSS 总和的中位数；共享页可能重复统计，不能与解析器的 physical footprint 等同。
所有阶段在同一进程中顺序运行，后续阶段包含之前的缓存。WebKit PID 通过测试副本中的诊断 getter 确认，正式应用没有加入私有诊断接口。
预览完成时间包含编辑器填充、页面导航、代码高亮、Mermaid 完成和两次动画帧；唯一 DOM 标记避免读到上一页。轮询间隔 20 ms，因此是近似端到端时间。

| 场景 | 延迟中位数：修复前 → 后 | 阶段末 RSS：修复前 → 后 | 修复后存活 WebView |
|---|---:|---:|---:|
| 原生编辑状态 | — → — ms | 149.2 → 155.4 MiB | 0 |
| 首次打开 5.1 KiB 小笔记预览 | 447.0 → 384.4 ms | 290.2 → 294.8 MiB | 1 |
| 切换 50 次小笔记 | 51.7 → 51.8 ms | 796.2 → 653.4 MiB | 1 |
| 继续切换 200 次（累计 250 次） | 51.9 → 51.7 ms | 808.3 → 658.7 MiB | 1 |
| 开关主窗口预览 30 次，最终关闭 | 219.3 → 219.8 ms | 231.0 → 224.6 MiB | 0 |
| 525.4 KiB 长文，加载 5 次 | 238.2 → 237.0 ms | 418.8 → 378.9 MiB | 1 |
| 120 个 Swift 代码块／3,600 行，加载 5 次 | 186.8 → 187.1 ms | 496.5 → 461.2 MiB | 1 |
| 20 个 Mermaid 流程图，加载 5 次 | 345.2 → 337.2 ms | 621.4 → 583.1 MiB | 1 |
| 打开并关闭 5 个独立预览窗口 | — → — ms | 696.1 → 237.8 MiB | 0 |
| 同一笔记双窗口与编辑定时器 | — → — ms | — → 238.9 MiB | 0 |
| 返回原生编辑器，再等待 10 秒 | — → — ms | 683.1 → 237.2 MiB | 0 |

普通小笔记切换约 51.7 ms。525.4 KiB 长文的同步填充中位数仍为 100.9 ms，主线程停顿仍可能可感知；此次没有将整个预览管线改为异步。
连续导航时 WebKit 的缓存开销仍然存在。此次修复解决了已确认的应用资源释放问题，不构成任意内容、任意运行时长的内存上限保证。

## 窗口与后台任务回归

通过正式 `openInNewWindow` 路径依次开关 5 个预览窗口，然后同时打开同一笔记的预览与编辑窗口。
关闭其中一个窗口后，另一个仍在 `AppDelegate.noteWindows` 中；调用正式编辑处理器启动 undo 定时器，再启动标签扫描，关闭窗口后定时器失效，待扫描笔记从队列中移除。
测试只保存对象弱引用。控制器、编辑器和文本处理器在窗口阶段检查释放；WebView 在返回主编辑器并等待 10 秒后检查全部释放，以容纳 AppKit/WebKit 的延迟释放。
测试回调使用明确的自动释放池，程序化关窗后推进 AppKit 事件循环；计时前激活测试窗口，防止后台动画帧节流污染结果。

完整应用最终 `leaks` 报告：430 个分配，21,552 字节（21.0 KiB）；修复前是 114,450 个分配、33,379,936 字节（31.8 MiB）。
正式渲染器资源释放与后台任务弱引用已通过专项／完整应用验证，最终报告没有 `NSBlockOperation` 根循环。
工具仍列出少量 `NSXPCConnection` 等分配，未逐项归因，因此不宣称整个进程绝对零泄漏。
